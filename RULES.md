# Linter rule registry

Source of the rules: skill `go-styleguide` (internal gid.team styleguide).
Related documents: [FINDINGS.md](FINDINGS.md) (backend-go audit: exceptions and missed rules), [FINDINGS_DDD.md](FINDINGS_DDD.md) (reverse audit: conventions extracted from backend-go code, candidates GID-218…223), [linter_framework.feature](linter_framework.feature), [rule_template.feature](rule_template.feature).

**Mandatory requirement: every rule has an eval.**
A rule is not considered ported until it has an executable eval:

- **go/analysis rules** — `analysistest` + `testdata/src/...` with `// want` comments;
- **pattern rules** (package `analyzers/patterns`) — the same `analysistest` + `// want`;
- the eval covers 4 case classes: positive (the violation is caught), negative (clean code passes), boundary, non-applicability (see the checklist in `rule_template.feature`).

Statuses: ✅ done · 🛠 in progress · 🔜 todo · ⛔ not portable (stays on review)

| GID-114 | entity-method-naming | Repo/service methods contain the entity name: `Job`, `Jobs`, `JobsByStageID`, `CreateJob`; no `ByID` suffix on single-item fetch (qualifiers `By<Field>ID` are allowed), no `List` prefix. The entity name is matched as a whole word, and so is every **leading part** of the receiver type name longer than two characters: the role suffix of a type is not part of its entity (`AdCabinetResolver` → `AdCabinet`, so `AdCabinet()` is legal, `Resolve()` is not), and a specialised entity may be called by its more general name (`SegmentBuildOutbox` → `EnqueueSegmentBuild`); a trailing plural `s` is the same word (`SegmentCleanup` → `CleanupSegments`). | GID-268 | ctor-dup-dependency | A constructor does not take the **same dependency twice under two different interfaces**: `marketplace.NewModule(datalab.SavedDatasetService(), datalab.ShowcaseService(), datalab.ShowcaseService())` hands one entity in under two roles, and the module then holds two fields pointing at the same object — a dependency list overstating how many collaborators it really has. The fix belongs to the **interfaces**, not to the call: merge them into one interface carrying both method sets (GID-134 declares them next to the consumer, so they are the consumer's to merge) and take the dependency as a single parameter. **Judged**: a call to a constructor (the `New`/`new` prefix by GID-104) — that is where the wiring of a module is written and where the duplicate is generated in bulk. An argument counts as "the same value" only in a form whose value is stable by inspection — a variable, a struct field, a **no-argument getter** — and it is matched by the **objects** behind the expression, not by source text: `left.showcase` and `right.showcase` are two values, `lab.ShowcaseService()` twice is one. A call **taking arguments** (`lab.ShowcaseFor("a")`) may return a fresh value every time and is not matched; `nil`, constants and function values are not dependencies to merge. **Both parameters must be different named interfaces declared in one package of the caller's module** (`sameModule`, the boundary GID-267 uses). Three deliberate silences follow: two parameters of **one and the same** interface (there is nothing to merge — a primary and a backup may legitimately be the same value), interfaces declared in **two packages** (merging would have to pick one of them as the home — a design decision, not a mechanical fix), and interfaces of **another module** — `io.Copy(rw, rw)` passes one value under `io.Reader` and `io.Writer` on purpose, and neither is ours to change. A **method-less** interface carries no dependency, the **variadic tail** holds no parameter of its own to name in a fix, and a call spreading a multi-value result (`newVault(both())`) is not judged. A `_test.go` file is not judged: a double is written to satisfy every interface of the constructor at once (GID-250 keeps it in the same package), and the fix — if there is one — belongs to the production wiring the rule already sees. **Exceptions**: `//nolint:giddupdep` or `settings.exclude` (`NewModule` \| `marketplace.NewModule`) (linter `giddupdep`) | owner decision 2026-08-24: an entity satisfying several interfaces is passed once, not once per interface | ✅ | ✅ |

## Not portable (stays on code review) ⛔

From the "partially checkable" set, chain-call-per-line → GID-196 and interface-minimal → GID-197
were implemented and moved to the registry (2026-06-07); the section is closed — by the decision
of 2026-06-07 the remaining heuristics were declared non-portable (the FP risk is unacceptable) and are listed below.

Name quality · verb-first naming of operations (verb-first-naming: a verb dictionary yields high FP — no deterministic formulation exists) · appropriateness of abstractions · completeness of error handling · method complexity · readability · business logic correctness · completeness of logging/metrics · SQL correctness in build functions · correctness of FSM transitions · a return type with fields the function cannot populate (styleguide.md#return-types) · SQL parameter style (`@id` in inline SQL vs `$1` in build functions — requires analysis of query strings) · field order of entity structs (ID → business fields → nullable → timestamps; high FP risk) · new-prefix-factories (unexported factories with the `new` prefix: the "what counts as a factory" heuristic yields unacceptable FP) · ptr-at-callsite (`&` at the call site rather than `&Type{}` upfront: usage analysis yields debatable diagnostics).

## Process for adding a rule

1. Add a row to this registry (ID, slug, source).
2. Specification — a `.feature` following the `rule_template.feature` template (4 case classes).
3. Implementation: an analyzer in `analyzers/<slug>/` (simple AST patterns go into the `analyzers/patterns` package).
4. **Eval is mandatory**: testdata with `// want`, all 4 case classes, `go test ./...` green.
5. Enable it in all three configs — `.golangci.yml` (self-lint), `gid-golangci.yml`
   (distributable) and `gid-golangci-rules.yml` (the `--gid-rules-only` profile);
   the gates are `TestDefaultConfigEnablesRegisteredLinters` and
   `TestRulesOnlyConfigMatchesDefault`. Update the status here.

### Test files

A test lives in the same package as the code under test (GID-250), so every rule sees `_test.go`
files too. Decide explicitly which side of the line the new rule is on, and cover the decision with a
non-applicability fixture:

- **Skips `_test.go`** (`internal/srcfile.IsTest`) when the test is *forced* to break the rule: a double
  copies the method names, signatures and types of the interface it fakes; a sentinel handed to that
  double has no home in `/domain/model`; a must-helper feeding a package-level fixture has no
  `*testing.T` to fail through. Rules about the placement of a package report per file and skip test
  files (and the synthesized `pkg.test` binary, `srcfile.IsTestBinaryPkg`) so as not to duplicate the
  production diagnostic.
- **Judges `_test.go`** when the test can follow the rule as easily as production code (uniform UUID
  generation, receiver naming, ranging over a slice of structs) — the diagnostic is then real, and the
  fix belongs in the test.

Incident 2026-08-04 (advertising-api): before this split, 173 of 497 diagnostics landed on test
scaffolding, and 167 of them were rule defects.
