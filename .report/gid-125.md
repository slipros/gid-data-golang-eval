# GID-125 — гейт применимости: правило судит только модуль, который реально говорит на SQL

## Повод

Прогон в consent-webhook-trigger: 28 диагностик на `entity.Document`, `Profile`, `Webhook`.
У сервиса нет базы — `internal/dal/repository/*` ходит по gRPC в `genproto/consentapi`,
entity наполняются из protobuf. Правило требовало db-тег на поля структур, которые в SQL
не попадают никогда. Это промах правила, а не долг кода.

Причина промаха: правило судило по пути (`/dal/entity`), а `/dal` говорит только о том,
где репозиторий **жил бы**, — не о том, что за ним есть база.

## Решение

Новый пакет `internal/sqlstack`: вердикт «модуль говорит на SQL» — хотя бы один
**собственный не-тестовый** файл модуля импортирует SQL-стек.

- Дефолтный список: `database/sql`, `jmoiron/sqlx`, `jackc/pgx`, `lib/pq`,
  `go-sql-driver/mysql`, `Masterminds/squirrel`, `ClickHouse/clickhouse-go`,
  `uptrace/bun`, `gorm.io/gorm`, `entgo.io/ent`. Мажорная версия и подпакет
  считаются той же библиотекой (`pathseg.SameLibrary` + префикс).
- `settings.sql-imports` заменяет список — сюда вписывается внутренняя обёртка,
  прячущая драйвер.
- Вердикт **на модуль**, кэшируется по корню (как `modlayout.HasDataLayer` у GID-160);
  читаются **импорты в коде**, а не `go.mod` — зависимость там может быть транзитивной.
- Импорт засчитывается в **любом** пакете модуля (`database/sql` в composition root
  включает правило для всего `/dal/entity`): база — это то, с чем говорит репозиторий,
  а он живёт рядом с entity.
- `_test.go` не засчитывается (фикстура может тянуть sqlmock в сервисе, который ничего
  не хранит); **сгенерированный код засчитывается** — sqlc и sqlboiler генерируют ровно
  тот SQL-слой, ради которого правило существует.
- Нет `go.mod` над пакетом (фикстура analysistest, пакет вне модуля) — вердикт
  «говорит на SQL», то есть догейтовое поведение.

Заодно из `internal/modlayout` экспортирован `Root(pass)` — обход вверх до `go.mod`
с кэшем уже жил там, дублировать его в `sqlstack` смысла не было.

GID-168 (`gidmodeltags`, запрет db-тегов в `/domain`) гейт не читает: тег в домене
неуместен независимо от того, что модуль хранит.

## Eval

- `internal/sqlstack` — юнит-таблицы: `scan` (sqlx в репозитории, `database/sql` только
  в composition root, pgx мажорной версии в подпакете, драйвер ClickHouse, gRPC-модуль,
  SQL только в `_test.go`, SQL в `vendor/` и `testdata/`, обёртка из настроек, пустой
  модуль), `isLibrary`, `HasStack` (включая пакет вне модуля).
- `analyzers/dbtags` — четыре фикстурных модуля со своими `go.mod`:
  `grpcsvc` (форма инцидента: репозиторий на gRPC, entity без тегов, **ни одного** `want`;
  плюс `repository_test.go` с импортом sqlx — не считается), `sqlsvc` (sqlx в репозитории —
  судится), `appsql` (`database/sql` только в `internal/app` — судится),
  `wrapsvc` (внутренняя обёртка + `settings.sql-imports`).
  Старые фикстуры (`svc`, `clickhouse`, `modeltags`) без `go.mod` — догейтовое поведение,
  ни одного `want` не тронуто.

Мутационная проверка: выключение гейта даёт 5 неожиданных диагностик на `grpcsvc`
(ровно форма инцидента); зачёт `_test.go`-импортов краснит 13 проверок.

## Гейты

- `go test -count=1 ./...` — весь eval репозитория зелёный;
- `make build-install` — ок;
- `make lint-fast` — **0 issues** (по ходу правил собственный линтер: errcheck/nilerr на
  `WalkDir`, GID-263 на новые экспортированные функции, goconst/perfsprint/GID-004 в тестах;
  подавления — только три `//nolint:gidstaticerr` на сентинелы `fs.SkipDir`/`fs.SkipAll`,
  которые `WalkDir` сравнивает по идентичности, и обёртка их сломала бы).

## Осознанно оставленное

- Замер по внешним репам (сколько находок сохранилось в consent-api, сколько погасло
  в event-api) не делал — деревья udmp локально не смонтированы. Прогон за владельцем.
- Модуль, который ходит в базу **только** через чужую обёртку, не перечисленную в
  `settings.sql-imports`, правило выключит (ложноотрицательное). Явный выход — вписать
  обёртку в настройки; это дешевле, чем гадать по именам пакетов.
